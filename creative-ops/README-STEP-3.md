# Creative Ops — Stage 3: API и машина статусов

## Реализовано

- Серверная проверка сессии через `getCurrentUser()` с повторным чтением роли из PostgreSQL.
- Единая матрица доступа в `src/lib/permissions.ts`.
- Машина переходов в `src/lib/status-machine.ts`.
- Транзакционный сервис задач в `src/server/services/task.service.ts`.
- Условное обновление статуса (`status` + владелец/исполнитель) для защиты от двойного взятия и конкурирующих переходов.
- `Serializable`-транзакция и обработка Prisma `P2034` как HTTP 409.
- ActivityLog в той же транзакции, что и соответствующее действие.
- Валидация входных данных через Zod.
- API для задач, переходов, комментариев, вложений, AI-расходов, переназначения и истории.
- Unit-тесты политики доступа, машины статусов и метрик времени.

## Матрица видимости

| Роль | Доступ к задачам |
|---|---|
| BUYER | Только задачи, созданные этим байером |
| CREATIVE | Все задачи NEW и задачи, назначенные этому креативщику |
| MANAGER | Все задачи |

Проверка выполняется на сервере для каждого запроса. UI не считается границей безопасности.

## API

Все эндпоинты требуют действующую NextAuth-сессию, кроме `/api/auth/[...nextauth]`.

| Метод | URL | Назначение |
|---|---|---|
| GET | `/api/tasks` | Список задач с фильтрами и пагинацией |
| POST | `/api/tasks` | Создать задачу (BUYER) |
| GET | `/api/tasks/:id` | Получить задачу и её детали |
| PATCH | `/api/tasks/:id` | Изменить ТЗ своей NEW-задачи (BUYER) |
| POST | `/api/tasks/:id/status` | Выполнить разрешённый переход статуса |
| POST | `/api/tasks/:id/comments` | Добавить комментарий |
| POST | `/api/tasks/:id/attachments` | Добавить ссылку на референс или результат |
| POST | `/api/tasks/:id/ai-usage` | Записать AI-расход (назначенный CREATIVE) |
| POST | `/api/tasks/:id/assign` | Переназначить активную задачу (MANAGER) |
| GET | `/api/activity` | История действий с фильтром по `action` и пагинацией |

### Фильтры списка задач

`status`, `priority`, `geo`, `offer`, `assigneeId`, `mine`, `page`, `limit`.

## Машина статусов

- `NEW -> IN_PROGRESS`: любой CREATIVE может взять свободную задачу. Взятие выполняется атомарно; повторный конкурентный запрос получает 409.
- `IN_PROGRESS -> REVIEW`: только назначенный CREATIVE; обязателен минимум один `RESULT`-attachment для текущего раунда.
- `REVIEW -> DONE`: только BUYER-владелец задачи.
- `REVIEW -> REVISION`: только BUYER-владелец задачи; обязателен комментарий, `revisionCount` увеличивается.
- `REVISION -> IN_PROGRESS`: только назначенный CREATIVE.
- Любой другой переход: HTTP 403.

Раунд вложений: `revisionRound = 0` — первая сдача; после первого возврата используется `revisionRound = 1` и т.д. `takenAt` фиксирует первое взятие и не перезаписывается, `submittedAt` обновляется на каждой сдаче, `completedAt` выставляется при приёмке.

## ActivityLog

Создание, изменение ТЗ, взятие, сдача, приёмка, возврат на правки, возобновление работы, комментарий, вложение, AI-расход и переназначение записываются в ActivityLog. Для переходов статуса запись создаётся в той же транзакции, что и изменение задачи.

## Ошибки API

Формат ответа:

```json
{
  "error": {
    "code": "INVALID_TRANSITION",
    "message": "Переход запрещён для вашей роли или этой задачи."
  }
}
```

Основные HTTP-коды: 400 — валидация, 401 — нет сессии, 403 — запрещённое действие, 404 — задача не найдена, 409 — конкурентное изменение, 500 — непредвиденная серверная ошибка.

## Тесты

```bash
npm run test:unit
```

Покрыты разрешённые/запрещённые переходы, требование результата и комментария, запрет менеджеру менять статусы, видимость задач по ролям и формулы времени.

## Ограничения этапа

- Вложения пока регистрируются как HTTP(S)-ссылки через API. Загрузка файла напрямую в Vercel Blob и безопасная выдача upload-токенов остаются отдельной задачей этапа UI/вложений.
- Интеграционные тесты с PostgreSQL и E2E в браузере требуют установленного окружения и заполненного `.env`.
